## 1. Структура проекта

```
rasp-hide/
├── manifest.json          # MV3, permissions: ["storage"]
├── background.js          # Service worker: тумблер, бейдж ON/OFF + счётчик
├── content/
│   ├── content.js         # Точка входа content script (IIFE)
│   ├── matcher.js         # Чистая логика: группы пар, точный матчинг (DOM-свободная, тестируемая)

├── lib/

├── tests/
│   └── matcher.test.js    # Юнит-тесты (Node, без chrome API)
```

`content_scripts`: `js: ["content/matcher.js", "content/ui.js", "content/content.js"]`, `matches: ["https://ro-rasp.tpu.ru/*"]`, `run_at: document_idle`.

## 2. Доменная модель

```ts
interface Rule {
  subject: string;          // видимое короткое название (нормализованное)
  teacher: string | null;   // null = «у всех», иначе ФИО
  enabled: boolean;
}

interface Settings {
  enabled: boolean;         // глобальный тумблер
  style: 'placeholder' | 'strike';
  rules: Rule[];
}
```

Хранение: `chrome.storage.sync` (ключи `enabled`, `style`, `rules`).
Дефолт: `enabled: true`, `style: 'placeholder'`, `rules: []`.

Инварианты набора правил (поддерживает `lib/rules.js`, едины для hover и options):

- Нет дубликатов (`subject + teacher` после нормализации) — при попытке: «Правило уже существует» + [Включить существующее].
- Поглощение: добавление/включение широкого правила (`teacher: null`) удаляет включённые узкие правила того же предмета. Чистая функция `wouldAbsorb(rule, rules): Rule[]` используется всеми местами изменения; удаление — всегда с подтверждением и списком удаляемых.
- Узкое правило при активном «у всех» того же предмета не добавляется: «Уже покрыто…» + [Включить существующее].
- Лимит 100 правил; `chrome.runtime.lastError` при записи → «Не удалось сохранить» (данные не теряются).

Матчинг преподавателя — по видимому ФИО (пользователи видят «Фамилия И. Я.»), id `/user_...` не используется — осознанный компромисс, пересмотр возможен в будущих версиях.

## 3. Content script

### 3.1. Чистая логика (`matcher.js`)

DOM-свободные функции (принимают NodeList/DOM-like интерфейс — для тестов мок):

- `splitIntoPairs(cellChildren): Node[][]` — группировка детей клетки на «пары»:
  - старт пары: `<div>`, содержащий `<b>` (тип ЛК/ПР/ЛБ) **или** (только если группа ещё не начата) `<span>` с названием;
  - `<hr>` прикрепляется к текущей паре;
  - остальные `<div>` (преподаватель, аудитория) — в текущую пару.
- `normalize(text): string` — trim, схлопывание пробелов и `&nbsp;`.
- `getPairName(pair): string | null` — видимое короткое название из первого `<div>` пары (`span.textContent`); `null`, если названия нет (ОВ/ОС) → пара не скрываема.
- `getPairTeachers(pair): string[]` — все видимые ФИО из ссылок `href="/user_..."`; у одной пары может быть несколько преподавателей (`ПР Преп1 <hr> Преп2` — одна пара), ФИО уникальны; пустой массив, если преподавателей нет.
- `matchRule(name, teachers, rule): boolean` — точное совпадение `name === rule.subject` (после normalize) и `rule.teacher === null` («у всех») **или** `rule.teacher` совпал хотя бы с одним ФИО из `teachers` (OR внутри пары: правило по любому преподавателю покрывает всю пару целиком).
- `isCellFullyHidden(cell): boolean` — все пары клетки скрыты (для решения по фону); вызывается только в режиме `placeholder` — в режиме `strike` фон клетки не трогается никогда.

### 3.2. Применение (`content.js`)

- Загрузка настроек → прогон по всем `#raspisanie-table td.cell`.
- Скрытие пары: `display: none` на всех элементах пары + вставка плейсхолдера-элемента (см. `ui.js`).
- `<hr>` пары скрывается/восстанавливается вместе с парой только в placeholder-режиме (фикс «старой полосы»); в strike-режиме `<hr>` **не** трогается — разделитель преподавателей одной пары (`ПР Преп1 <hr> Преп2`) формально остаётся видимым, как и вся пара.
- Одна пара с несколькими преподавателями («ПР Преп1 <hr> Преп2») — это **одна** группа пар, а не две: `<hr>` прикрепляется к текущей паре (см. 3.1), преподаватели берутся из первого `<a href="/user_...">`, правило применяется ко всей паре целиком.
- Фон клетки: если все пары скрыты → `background-color: transparent !important`; иначе восстановить исходный `style` (сохраняется в `WeakMap` при первом скрытии; исходный атрибут `style` кэшируется **до** любых изменений).
- `MutationObserver` на `document.body` (childList + subtree) с дебаунсом ~120 мс — повторное применение при перерисовке/расшифровке.
- `chrome.storage.onChanged` → переприменение без полной перезагрузки; при `enabled: false` — полный откат (см. 3.4) и `{type:'off'}` в SW.
- Счётчик скрытых пар текущей страницы → `chrome.runtime.sendMessage({type:'count', value})` (в SW для бейджа).

### 3.4. Полный откат (глобальный OFF)

- По `chrome.storage.onChanged` (`enabled: false`): удаляются все `rh-*` элементы (плейсхолдеры, hover-кнопки, меню), исходные стили восстанавливаются из `WeakMap`, hover-UI не работает (правила добавлять нельзя). Никакого «полускрытого» состояния. Каждая вкладка откатывается сама и сама чинит свой бейдж (`{type:'off'}`).

### 3.3. Hover-UI (`ui.js`)

- Для каждой пары (кроме пар без названия) создаётся overlay-кнопка «Скрыть» (position: absolute внутри td; td получает `position: relative` без перезаписи существующих стилей).
- Клик → кастомное мини-меню: у пары с одним преподавателем — 2 пункта («Скрыть: ФИО» / «у всех») + «Отмена»; у пары с несколькими преподавателями — **отдельный пункт «Скрыть: ФИО» на каждого преподавателя** пары + «у всех» + «Отмена»; у пары без преподавателя — один пункт «Скрыть пару» (эквивалент «у всех»). Меню — DOM-элемент внутри клетки, закрывается по клику вне и Escape.
- Поглощение при «Скрыть у всех»: через `wouldAbsorb` из `lib/rules.js`; при непустом списке меню превращается в подтверждение «Также удалится: …» ([Удалить] / [Отмена]).
- Скрытая пара: вместо содержимого — плейсхолдер «скрыто» (бледный, занимает место). Hover на плейсхолдер → кнопка «Вернуть».
- Все добавленные элементы имеют префикс-класс `rh-*` и удаляются/пересоздаются при повторном прогоне.

## 4. Background (service worker)

- `chrome.action.onClicked` — инверсия `enabled` в storage.
- Бейдж — per-tab (`chrome.action.setBadgeText({ tabId, text })`), право `tabs` не требуется:
  - `{type:'count', value}` от content script → зелёная цифра (в т.ч. «0») для `sender.tab.id`;
  - `{type:'off'}` → серый «OFF» для `sender.tab.id`;
  - `chrome.tabs.onUpdated` — очистка бейджа вкладки при начале навигации; если это снова расписание, content script выставит счётчик.
- Текст «ON» не используется: цвет + цифра его заменяют.
- `chrome.runtime.onMessage` — только приём `{count|off}`.
- Никакой сети. `onInstalled` — инициализация дефолтных настроек, если их нет.

## 5. Options

- Форма: тумблер, radio стиля, список правил (subject + teacher/«все» + enabled + delete), добавление вручную, сброс к дефолту.
- Список: сортировка (алфавит предмета, «все» выше конкретных ФИО), поиск-фильтр по subject, счётчик «N/100» (при 100 добавление блокируется).
- Добавление вручную: свободный ввод ФИО + подсказка «введите ФИО точно как в расписании» (автокомплит — кандидат в v2).
- Все записи — через общий `lib/rules.js` (единый формат, валидация, дубликаты/поглощение, обработка `lastError`).
- «Сброс к дефолту» — с подтверждением, сбрасывает только `rules` (не трогает `enabled`/`style`).

## 6. Тестируемость

- `matcher.js` пишется без зависимостей от chrome/DOM; тесты на Node с простыми моками элементов (как в текущем `test_lib.js`).
- Тест-кейсы: 1 пара; 2 пары через `<hr>`; 3 пары (2 скрываемые + 1 нет); пара без названия (ОВ/ОС) не скрываема; точное совпадение с подгруппами (A1.1 ≠ B1); «у всех» vs «конкретный преподаватель»; нормализация пробелов/NBSP; выключенные правила; одна пара с двумя преподавателями через `<hr>` внутри группы (встречается на сайте: «ПР Преп1 <hr> Преп2») — группа не разбивается, `<hr>` прикрепляется к паре, `getPairTeachers` возвращает обоих, матчинг «у преподавателя» — по **любому** из ФИО (OR).

## 7. Безопасность и соответствие CWS

- `permissions: ["storage"]` только.
- Нет `host_permissions` (content_scripts.matches достаточно; сеть не используется).
- Нет eval/remote code; всё внутри пакета.
- Content script не отправляет данные наружу; в SW — только счётчик для бейджа.
- DOM-изменения только со стороны content script; SW не имеет доступа к DOM страницы.
